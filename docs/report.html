@barocss/doc-sync Report

A report on a collaboration CRDT, synchronization server, and browser demo built in dependency-free TypeScript without Yorkie. The document is stored as token lines. An externally supplied schema defines block types.

83 tests passed 3000 random scripts × 2/4 participants × GC off/on — 0 divergences · 0 editor mirror mismatches 10 concurrent browser windows — identical document 0 CRDT/server dependencies (only ProseMirror integration uses prosemirror) 500 random ProseMirror scripts — identical document 11,519 code lines, including tests Location: this repository · uncommitted

Summary

  • A document is a token line. Enter inserts one block marker; paragraph merge deletes one marker. There is no tree-cut or node-move operation.
  • RGA ID comparison determines order. Concurrent Enter at the same position forms one line through a boundary key.
  • Undo is per participant. Undoing a deletion cancels only that participant's specific deletion, preventing the yorkie#2237 pattern.
  • Server receipt order is causal order. Changes are validated and applied atomically. GC is a log entry and compacts tombstones only through the frontier determined by acks and undo pins.
  • The CRDT has no block-type knowledge. It receives an injected schema and knows only 9 shapes: text, inline, flow, group, grid, row, cell, atom, and span. The 5 wire operations are type-independent.
  • Tables use row lines × column lines; IDs address cells. Concurrent row/column insertion, column deletion versus cell input, merged cells (colspan/rowspan), and cell backgrounds converge.
  • Lists and captions are stored flat and displayed as groups. An item enters or leaves a list through one type change, without moving blocks.
  • Model output is a tree shaped like a schema-based document editor's JSON (table > table-row > table-cell > table-cell-body, image-component > image > inline-image, and so on).
  • Editors send five model operations (insert · delete · update · split · merge) using model paths. Names and semantics match a schema-based document editor's manipulation engine. Per-row cell insertions fold into one column.
  • Receivers get only changed regions through the same five operations. Events are verified before emission and fall back to full replacement on failure. Across 3000 random scripts, hundreds of thousands of events had 0 mismatches.
  • Cursors and selections are stored as token keys and converted to paths, so other users' edits do not shift their anchors.
  • ProseMirror is integrated. Steps become model operations (one split for Enter), and remote changes use one minimal replacement. Across 500 random scripts using real ProseMirror commands, all editors, CRDTs, and the server had identical documents.

Why It Was Built

The earlier Yorkie collaboration-plugin experiment copied a schema-based document editor's document directly into Yorkie Tree. Most issues found during research came from tree-cut operations.

  • Concurrent cuts at the same boundary move different nodes on different replicas (§7.4, yorkie#2240). Two users pressing Enter at the same position can lose text or diverge.
  • Undo restores another user's deletion that it never observed (yorkie#2237).
  • Yorkie events omit split depth (splitLevel), forcing receivers to infer it.
  • Three designs that carried decisions in operations were tested. All performed worse than the baseline.

In the same research, removing the inline layer and using a flat structure greatly reduced divergences (172 → 51). The Yjs comparison also showed that representation, rather than the CRDT, made the difference. The question became: how would an implementation built from a representation without tree cuts behave? This repository answers that question.

Documents as Token Lines

There are three token kinds: character tokens (one character), node tokens (block marker ¶, table, row, image, and so on), and head tokens (line start). Block lists are not stored. They are calculated by reading live tokens in order.

  • Enter = insert one text marker. Backspace merge = delete one marker.
  • Block type (heading, quote, list item) is the marker attribute $type.
  • The model is a function of live tokens only. It does not read tombstones, so it is independent of GC timing.

Order and Same-Position Enter

RGA: Order from IDs Alone

Every token has an immutable ID, lamport@participant. New tokens are inserted after a left reference token. Among concurrent insertions at the same reference, the larger ID comes first. Decisions depend only on IDs, so all replicas produce the same line despite different receipt orders.

Boundary Keys: One New Line for Concurrent Enter at One Position

A text marker records the creator's observed boundary (left token | right token). If several live markers share a boundary, only the first in order opens a block; the others are absorbed.

Independent Enter at the Same Position

Same boundary → one line. Text typed by each participant remains in that line. Four concurrent participants also produce one line containing all four inputs.

Enter After Observing Another Enter

Different left token and boundary → separate lines. Two consecutive Enters by one user produce two empty lines.

Deletion Records and Undo

Deleted tokens are retained. Each token records the operations that deleted it and cancelled deletions. It is a tombstone while any uncancelled deletion remains.

Undo is separate per participant. It sends new inverse operations rather than returning to an earlier document.

Undo TargetSent OperationContract
InsertionNew deletionPreserve text typed by others in between
DeletionCancel only that deletion (undel)If another user concurrently deleted the same character, it stays deleted. This structurally prevents yorkie#2237.
Type, attributes, marks, cell color, cell mergeset to the previous valueOnly while the current write is still mine. Do not overwrite another user's later change.
Table/row/column insertion or deletionRestore/deleteUndoing column deletion restores its cell text, including others' input, and colors.

Editor behavior: consecutive typing forms one unit within 1.5 seconds while the cursor remains contiguous. Undo restores the pre-edit cursor, stored as token IDs. Replacing a selection is one unit. Retain the latest 100 units.

Lines and Slots

The document has more than one body line. Each node has named slot lines. A slot head ID derives from its owner node ID and slot name (0@owner/slot), so no operation creates the line. Every replica creates the same head when first needed.

Virtual Positions

If no text block with its own marker follows a table, image container, or divider, the model provides a virtual block. This gives cursors a position around tables and receives concurrently inserted text immediately after a table. Changing the virtual block's type creates a marker then.

Five Wire Operations

Every insertion identifies the token after which to insert. This is independent of block type.

OperationShapeUse
text{id, origin, text, marks?}n characters with consecutive IDs
node{id, origin, type, boundary?, attrs?}Block marker (Enter), table/row/column, container, divider, inline image
del{at, ids}Deletion, cancellable later using the same at
undel{at, cancels, ids}Cancel only the specified deletion: undo
set{at, ids, key, value}LWW writes: block type $type, block/image attributes, character marks, cell attributes $cell:row,col|name, cell merge $span:row,col

Receiving the same operation twice gives the same result (idempotence). Deletion and attribute operations targeting compacted or absent tokens are silently skipped.

Synchronization and Server

  • Server order = causal order. If an operation references a token, that token is already in the log with an earlier sequence. Participants store only the last received serverSeq, without a version vector.
  • Local edits apply immediately without waiting for the server. No rebase is needed.
  • Offline edits are queued and retransmitted. The server deduplicates by (actor, seq).
  • Atomic application: before application, the server validates every operation in a change, including tokens created by earlier operations in that change. Any invalid operation rejects the entire change with 409 and leaves the document unchanged.
  • Server restart replays the log to continue. Logs from the pre-schema version (v2) can also be read.

GC: Tombstone Compaction

Tombstones stay in their lines. Removing them would change RGA comparisons among tokens with the same origin and misplace late operations. Instead, compact stable tombstones: discard content and records but retain positions. Consecutive tombstones from one participant merge into one token (▒×N6A). This span behaves like the original characters for ordering.

frontier = min over participants ( received ack , undo pin − 1 )
  • Received sequence (ack): later operations from that participant already observed the deletion, so they do not reference the compacted token.
  • Undo pin: the earliest deletion that my undo can cancel. Compact only before it.
  • Disconnected participants are awaited for 2 minutes. Closing a window removes it immediately.
  • Acks travel in order through the same channel as Changes. Overtaking could compact a reference token needed by an unsent operation.
  • GC is itself a log entry, {serverSeq, gc: frontier}. Every replica performs the same compaction at the same log position. The server automatically runs GC when more than 12 compactable tombstones accumulate.

Character marks have two forms: boolean marks (marks: bold/italic/underline/strike) and value marks (markValues: link URL, validated by pattern). New characters inherit only boolean marks.

Attribute specifications include default, values (allowed values), min/max, pattern (regular expression, for example colors), inherit (inherit on Enter), and computed (CRDT-generated colspan/rowspan/spanned). Editor display uses ui (label, list, variants, placeholder).

Validation Uses Only Immutable Facts

The schema lets the server validate whether a type is allowed in a line and whether an attribute value is valid. It uses only the token's owning line and the node's original type at creation. Current type and liveness can differ among replicas. Rejecting based on them would separate the server from a participant that already applied its edit locally.
  • Validation is therefore line-level: accept an inline node if any text type allowed in that line accepts it.
  • The server can run without a schema. Ordering, application, and GC stay the same; only validation is reduced. Tests confirm this.
  • Across 12,000 random runs (3000 scripts × 2/4 participants × GC off/on), server validation rejected 0 client-generated operations. Rejection is an error in the harness.

It builds a raw tree from storage, then applies canonical normalization (model.ts canonical: list grouping, attribute defaults, text-run merging, and table-cell alignment). The editor model uses the same rules, so both have the same shape. Empty virtual positions after tables are absent from the model.

Block Behavior

Character Marks

  • LWW applies per character, not per range. A mark operation targets the IDs observed by its creator. Characters inserted into that range by others remain unchanged.
  • New characters inherit marks from the left character, excluding links.
  • Links use a per-character link URL (LWW). The model groups consecutive identical URLs into one inline-hyperlink. Concurrent different URLs use the later write.
  • Inline images are skipped.

Lists: Flat Storage

  • A list-item is a text block in a flow line (listType/level). The model groups consecutive items into a list.
  • Storing real containers would require a block move whenever an item entered or left. Flat storage needs only a type change, preserving text typed concurrently while an item leaves.
  • Numbering is calculated in the view. The schema-based document editor also stores lists through attributes.

Images and Captions

  • An image-component container line holds an image block (no text, one inline-image) followed by caption-paragraph blocks. Captions display as groups, like lists.
  • Captions do not merge into image blocks through Backspace, Delete, or range deletion.
  • Concurrent image-size changes use the later write.

Callouts and Dividers

  • A callout is a container with one body line containing lists, tables, and images.
  • A divider is an atom. Backspace at the start of the following block deletes it.
  • Callout color (tone) is an LWW attribute.

Tables

A table node owns a rows line (table-row nodes) and a cols line (column nodes). Cells are slot lines addressed by (row, column) ID pairs; each line is a table-cell-body. The schema does not fix row/column counts. Choose them on insertion, then add or remove them later.

Concurrent ActionsResult (Identical on All Replicas)
A adds a row; B adds a column.3×3. The intersection of independently created row and column is immediately writable.
A deletes a column; B writes into one of its cells.Column disappears. B's text remains live in the hidden cell and returns when A undoes.
A deletes the table; B writes into a cell.Table disappears. Undo restores B's text too.
Two users each delete one of the two remaining rows.A table without rows is entirely hidden.
Concurrent Enter at the same cell position.One new line, as in the body.
Insert two tables at the same position.Both remain in identical order.
Another user deletes my current column.Cursor moves to an adjacent cell.

Cell Merging (colspan · rowspan)

Cells have no tokens, so merges are stored as table-node attributes, $span:topLeftRow,topLeftCol = {endRow, endCol} (IDs, LWW). Like a schema-based document editor, the model is a full grid: every row has every cell; the top-left cell has colspan/rowspan, and hidden cells have spanned: true.

  • Dimensions use endpoint IDs instead of counts, so columns concurrently inserted inside a merged region are covered too. Deleting the endpoint column shrinks it.
  • Deleting the top-left cell's row or column removes the merge and exposes its hidden cells.
  • Concurrent overlapping merges retain only the one with the later ID.
  • Hidden cell text remains stored and reappears on unmerge. Collecting text during merge would copy it and separate text concurrently typed into that cell.

Cell Backgrounds

Similarly, table-node $cell:row,col|backgroundColor stores backgrounds. Only non-computed table-cell schema attributes are writable; colors must match #rrggbb (pattern). Colors attach to row/column IDs, so preceding insertions do not change the target cell. Undoing column deletion restores its color too.

Edit API: Five Model Operations

Editors need no CRDT line/token knowledge. They use model paths (child indexes in toJSON, shaped like a schema-based document editor's numeric tree paths) and model nodes. Five operations share names and semantics with that editor's manipulation engine.

doc.edit([
    {op: "delete", at: [0], count: 1},                                       // Editor full-content replacement pattern
    {op: "insert", at: [0], content: [{type: "paragraph", runs: [{text: "after", marks: {}}]}]},
]);
doc.edit([0, 1, 2].map(r => ({op: "insert", at: [1, r, 1], content: [{type: "table-cell"}]})));   // One cell per row = one column
doc.edit([{op: "update", at: [1, 0, 0], attrs: {colspan: 2, backgroundColor: "#dcfce7"}}]);
doc.edit([{op: "split", at: [2, 4]}]);                                       // Enter
OperationBy Shape
insertInside text → characters/inline; block inside text → split there and insert between; flow/list → blocks (tables include rows, columns, cells, merges, and cell attributes); table → row; row → column.
deleteCharacters, whole blocks, rows, columns; deleting the last row/column deletes the table.
updateBlock type (type)/attributes; list node → every item; text range (length) → marks; cell → cell attributes/colspan/rowspan.
splitEnter. Boundary keys use left/right tokens at compilation. Schema next/inherit apply.
mergeMerge into the preceding text block by deleting the marker. Skip if the preceding block cannot receive text.

Two Forms of Batch State

  • Empty head: deleting a flow's first block retains its line head (always the first block) as an empty position. Later paths in the same batch do not count it; a leading text block fills it. If it remains empty, the next text block is pulled into it. This preserves a schema-based document editor's delete-and-reinsert pattern.
  • Column folding: a schema-based document editor's tree has no columns, so column insertion/deletion arrives as the same cell index in every row. Consecutive operations on the same table and cell index fold into one column node. An operation on only one row also normalizes to one column.

Normalize: Differences to Send Back to the Editor

edit() returns generated wire operations plus normalize. These edits reconcile the CRDT model with the result of applying the original batch directly to the editor model. They are usually empty.

CaseReason
Insert a cell in only one row.Normalize to one column, with empty cells in other rows.
Insert a column/row inside merged cells.Merge endpoints use IDs, so the new column is covered too. The editor leaves colspan unchanged.
Overlapping cell merges.Retain only the later merge.
Delete a table before a virtual position containing text.Virtual text joins the preceding block; occurs only during collaboration.

Each run of 3000 random scripts produced 8–9 local edits with normalize, all from the cases above.

Migration from Former Edit Functions

Moved 18 edit functions (insertText, splitBlock, insertAxis, setSpan, and so on) into commands.ts. Commands only translate human actions to model operations. Old functions and new commands ran in parallel from identical state (1000 scripts × 40 steps). After confirming 0 differences across 34,001 steps, the old functions were removed. One initial difference in the cell-merge already-equal-value check was fixed.

Receiving Events

client.onModelEvents = (events, info) => … returns model operations that convert the previous model to the next when remote changes, undo, or snapshots change the model. Editors apply them to their own models.

  • Events come from comparing models before and after receipt. Only changed regions are emitted: one character insertion, one cell per row for a column (the schema-based document editor's operation shape), or a cell update for a background color.
  • Flows are compared as flattened item sequences. Each generated operation is applied to a working copy, which supplies the next path. Initial grouped-list comparison failed when an inserted list immediately joined its neighbor and shifted subsequent paths. Mirror tests found this.
  • Before emission, apply events to the previous model for verification. On failure, fall back to full-document replacement (info.fallback). There were 0 fallbacks across 3000 random scripts.
  • The initial proposal translated wire operations one by one. Model comparison provides the same precision and handles invisible changes, such as absorbed markers, virtual positions, and hidden cells, without separate cases.

Limits and Missing Features

Missing FeatureReason / Approach
Editor adapterThe edit API matches a schema-based document editor's operations. Remaining conversion: inline-text paths to character positions, fold two-stage Enter (split [0,0,5]/split [0,1]), and align list representation (paragraph + listGroupId in that editor).
Flows start with text blocksA CRDT line head is always a text block. If the other editor starts with a table, this model has an empty leading paragraph. The adapter must align them.
Multi-cell selectionSelection stays within one line: body, one cell, or one callout.
Exactly one required childThe schema cannot express one image and one caption (min/max). Commands enforce this today. Handcrafted operations could create a second image or an image without a caption.
Validation precisionValidation is line-level. An image-container line containing captions accepts characters, so the server cannot reject handcrafted input into an image block. Block-level validation requires identical block membership on all replicas, but that depends on current state and can differ.
Collecting text during mergeText in covered cells is only hidden. Collecting would copy text and separate concurrent input.
Row/column attributesRow height and column width can be added as row/column-node attributes.
PerformanceOne token per character; models recompute from scratch per edit, and receiving events compare two models per receipt. Consecutive-character grouping and incremental calculation are needed.
Long-disconnected participantsAfter 2 minutes they leave the GC frontier. Returning and undoing a compacted tombstone could diverge. Reconnection from a snapshot needs implementation.
Authentication, authorization, multiple serversDemo level. Per-document routing to one server enables horizontal scaling. Download uses SSE; WebSocket is preferable for production use.

const client = new SyncClient("A-1x2y", new HttpTransport("demo", "A-1x2y"), {schema: DEMO_SCHEMA});

client.connect();

const doc = client.doc;

// 1) Editor commands: convert human actions to model edits, apply immediately, and return wire operations
client.commit(cmd.insertText(doc, {b: 0, o: 0}, "hello"), {caretBefore: "", caretAfter: ""});
client.commit(cmd.insertBlock(doc, {b: 0, o: 5}, "table", {rows: 2, cols: 3}));

const table = doc.blocks()[1] as GridBlock;

client.commit(cmd.setSpan(doc, table, 0, 0, 1, 2));                    // Merge 1×2
client.commit(cmd.setCellAttr(doc, table, 1, 2, "backgroundColor", "#dcfce7"));
client.commit(cmd.setLink(doc, {b: 0, o: 0}, {b: 0, o: 5}, "https://example.com"));

// 2) Or use model operations directly, matching a schema-based document editor
const {ops, normalize} = doc.edit([{op: "insert", at: [1, 1, 0, 0, 0, 0], content: "cell text"}]);

client.commit(ops);                     // Apply nonempty normalize to the editor model too

// 3) Receiving: remote changes to the editor model
client.onModelEvents = (events, info) => editorModel.apply(events);

// 4) Selection: store token keys, then convert to paths
const key = anchorAt(doc, [0, 3]);      // ... after receiving remote changes
const path = pathAt(doc, key);

client.undo();                           // Undo only my last edit
console.log(JSON.stringify(doc.toJSON()));   // Tree shaped like an editor document
