동시편집 연구 · 2026-10-22

@barocss/doc-sync 보고서

Yorkie 없이, 의존성 없는 TypeScript 로 만든 동시편집 CRDT·동기화 서버·브라우저 데모의 정리. 문서를 트리가 아니라 토큰 줄로 들고, 블록 종류는 바깥에서 주입한 스키마가 정한다.

시험 83개 통과 무작위 3000 대본 × 참여자 2·4 × GC 끔·켬 — 갈림 0 · 편집기 거울 어긋남 0 브라우저 창 10개 동시 — 같은 문서 CRDT·서버 의존성 0 (ProseMirror 연동만 prosemirror) ProseMirror 무작위 500 대본 — 같은 문서 코드 11,519줄 (시험 포함) 위치 이 저장소 · 커밋 안 함

요약

  • 문서는 토큰 줄이다. Enter 는 블록 표지 하나 넣기, 문단 합치기는 표지 하나 지우기다. 트리를 자르거나 노드를 옮기는 연산이 없다.
  • 순서는 RGA(이름표 비교) 하나로 정한다. 같은 자리 동시 Enter 는 경계 키로 한 줄로 모인다.
  • 되돌리기는 참여자별이고, 지운 것을 되돌리면 내가 한 그 지우기만 취소한다 (yorkie#2237 꼴이 생기지 않는다).
  • 서버는 받은 순서가 곧 인과 순서다. 변경은 한 덩어리로 검사·적용된다. GC 는 로그의 한 줄이고, ack 와 되돌리기 핀으로 정한 기준점까지만 묘비를 압축한다.
  • CRDT 는 블록 종류를 모른다. 스키마를 주입하고, CRDT 는 모양 9가지(text·inline·flow·group·grid·row·cell·atom·span)만 안다. 전선 연산은 종류와 무관한 5가지다.
  • 표는 행 줄 × 열 줄이고 칸은 이름표로 가리킨다. 행·열 동시 추가, 열 지우기 대 칸 입력, 칸 합치기(colspan·rowspan), 칸 배경색까지 수렴한다.
  • 목록·캡션은 평평하게 저장하고 묶어서 보인다. 항목이 목록에 들고 나는 것이 블록 옮기기 없이 종류 바꾸기 하나로 끝난다.
  • 모델 출력은 스키마 기반 문서 에디터의 문서 JSON 과 같은 꼴의 트리다 (table > table-row > table-cell > table-cell-body, image-component > image > inline-image …).
  • 편집기는 모델 연산 다섯 가지(insert · delete · update · split · merge)를 모델 경로로 보낸다 — 스키마 기반 문서 에디터의 문서 조작 엔진과 같은 이름·뜻. 그 에디터에서처럼 행마다 오는 칸 넣기는 열 하나로 접는다.
  • 받는 쪽은 바뀐 곳만 같은 다섯 가지 연산으로 받는다. 내보내기 전에 검산하고, 틀리면 통째 바꾸기로 물러선다. 무작위 3000 대본에서 이벤트 수십만 개, 어긋남 0.
  • 커서·선택은 토큰 키로 들고 있다가 경로로 바꾼다 — 남의 편집에 밀리지 않는다.
  • ProseMirror 도 붙었다. Step 을 모델 연산으로(Enter 는 split 하나), 남의 변경은 최소 교체 하나로. 진짜 ProseMirror 명령으로 돌린 무작위 500 대본에서 모든 편집기·CRDT·서버가 같은 문서.

왜 만들었나

앞선 Yorkie 실험의 동시편집 플러그인은 스키마 기반 문서 에디터의 문서를 Yorkie Tree 에 그대로 옮겼다. 연구하면서 드러난 문제는 대부분 트리를 자르는 연산에서 나왔다.

  • 같은 경계를 동시에 자르면 복제본마다 다른 노드를 옮긴다 (§7.4, yorkie#2240). 둘이 같은 자리에서 Enter 를 치면 글이 사라지거나 문서가 갈린다.
  • 되돌리기가 보지 못한 남의 삭제까지 되살린다 (yorkie#2237).
  • Yorkie 이벤트에는 나누기 깊이(splitLevel)가 실려 오지 않아, 받는 쪽이 짐작해야 한다.
  • "판단을 연산에 실어 보내는" 설계 셋을 시험했지만 모두 기준보다 나빴다.

같은 연구에서 인라인 요소 층을 없앤 평평한 구조가 갈림을 크게 줄였고(172 → 51), Yjs 비교에서도 차이를 만든 것은 CRDT 가 아니라 표현이었다. 그래서 질문을 바꿨다 — 트리를 자르지 않는 표현으로 처음부터 만들면 어떻게 동작하나. 이 저장소가 그 답이다.

문서는 토큰 줄

토큰은 셋이다. 글자 토큰(한 글자), 노드 토큰(블록을 여는 표지 ¶, 표, 행, 그림 …), 머리 토큰(줄 맨 앞). 블록 목록은 저장하지 않는다. 살아 있는 토큰을 앞에서부터 읽으며 그때그때 계산한다.

  • Enter = text 표지 하나 넣기. Backspace 로 합치기 = 표지 하나 지우기.
  • 블록 종류(제목·인용·목록 항목)는 표지의 속성 $type 이다.
  • 모델은 살아 있는 토큰만의 함수다. 묘비를 읽지 않으므로 GC 시점과 무관하다.

순서와 같은 자리 Enter

RGA — 이름표만으로 순서를 정한다

모든 토큰에는 바뀌지 않는 이름표 lamport@참여자 가 붙는다. 새 토큰은 "왼쪽 기준 토큰" 바로 뒤에 들어가되, 같은 기준 뒤에 동시에 들어간 토큰끼리는 이름표가 큰 쪽이 앞에 선다. 판단에 쓰는 값이 이름표뿐이라, 받는 순서가 달라도 모든 복제본에서 같은 줄이 나온다.

경계 키 — 같은 자리 동시 Enter 는 새 줄 하나

text 표지에는 만든 쪽이 본 경계(왼쪽 토큰 | 오른쪽 토큰)가 적힌다. 같은 경계를 가진 살아 있는 표지가 여럿이면 순서상 첫 것만 블록을 열고 나머지는 흡수된다.

서로 모르고 같은 자리에서 Enter

경계가 같다 → 한 줄. 각자 그 줄에 친 글자는 모두 그 줄에 남는다. (넷이 동시에 쳐도 한 줄에 넷)

상대의 Enter 를 보고 다시 Enter

왼쪽 토큰이 달라 경계가 다르다 → 따로 줄. 혼자 Enter 두 번이면 빈 줄 둘.

지우기 장부와 되돌리기

토큰은 지워도 없애지 않는다. "나를 지운 연산들"과 "취소된 지우기들"을 기록하고, 취소되지 않은 지우기가 하나라도 남아 있으면 묘비로 친다.

되돌리기는 참여자마다 따로 있고, 과거로 돌아가는 것이 아니라 반대 연산을 새로 보낸다.

되돌리는 것보내는 연산지키는 약속
넣기새 지우기그 사이 남이 친 글자는 그대로
지우기그 지우기만 취소 (undel)남이 동시에 같은 글자를 지웠으면 계속 죽어 있다 — yorkie#2237 이 구조적으로 안 생긴다
종류·속성·서식·칸 색·칸 합치기직전 값으로 set지금 값이 아직 내가 쓴 값일 때만. 남의 나중 변경을 덮지 않는다
표·행·열 넣기·지우기살리기·죽이기지운 열을 되돌리면 그 열 칸의 글(남이 쓴 것 포함)과 색까지 돌아온다

편집기 쪽: 이어 친 글자는 한 단위(1.5초 안, 커서가 이어질 때), 되돌린 뒤 커서는 편집 전 자리(토큰 이름표로 기억), 선택을 덮어 치기는 한 단위, 최근 100단위.

줄과 자리 (slot)

줄은 본문 하나만 있는 것이 아니다. 노드마다 이름 붙은 자리 줄이 있다. 자리 줄 머리의 이름표는 주인 노드 이름표와 자리 이름에서 정해지므로(0@주인/자리), 줄을 만드는 연산이 따로 없다. 모든 복제본이 처음 필요할 때 같은 머리를 만든다.

빈 자리 (virtual)

표·이미지 그릇·구분선 바로 뒤에 자기 표지를 가진 text 블록이 없으면, 모델이 빈 자리 블록을 하나 둔다. 그래서 표 앞뒤에는 언제나 커서를 둘 곳이 있고, 표 바로 뒤로 동시에 들어온 글자도 갈 곳이 있다. 빈 자리의 종류를 바꾸면 그때 표지가 새로 생긴다.

전선 연산 다섯 가지

무엇을 넣든 "어느 토큰 뒤"만 말한다. 블록 종류와 무관하다.

연산모양쓰는 곳
text{id, origin, text, marks?}글자 n 개 (이름표 연속)
node{id, origin, type, boundary?, attrs?}블록 표지(Enter), 표·행·열, 그릇, 구분선, 글 안 그림
del{at, ids}지우기 (같은 at 으로 나중에 취소 가능)
undel{at, cancels, ids}지정한 지우기만 취소 — 되돌리기
set{at, ids, key, value}LWW 쓰기: 블록 종류 $type, 블록·그림 속성, 글자 서식, 칸 속성 $cell:행,열|이름, 칸 합치기 $span:행,열

같은 연산을 두 번 받아도 결과가 같다(멱등). 압축됐거나 없는 토큰을 가리키는 지우기·속성은 조용히 지나간다.

동기화와 서버

  • 서버 순서 = 인과 순서. 누가 어떤 토큰을 기준으로 삼았다면 그 토큰은 이미 앞 번호로 로그에 있다. 참여자는 버전 벡터 없이 "마지막으로 받은 serverSeq" 하나만 기억한다.
  • 내 편집은 서버를 기다리지 않고 바로 적용한다. 되감기(rebase)가 필요 없다.
  • 끊긴 동안 친 것은 쌓아 두었다가 다시 보낸다. 서버가 (actor, seq) 로 중복을 거른다.
  • 한 덩어리 적용: 서버는 적용 전에 변경 안의 모든 연산을 검사한다(같은 변경 안에서 앞 연산이 만든 토큰도 셈에 넣는다). 하나라도 틀리면 409 로 통째로 거절하고 문서는 그대로다.
  • 서버를 다시 켜면 로그를 되풀이해 이어 간다. 스키마 이전 판(v2)의 로그도 읽어 들인다.

GC — 묘비 압축

묘비를 줄에서 빼지 않는다. 빼면 RGA 의 "같은 기준 뒤 이름표 비교"가 달라져 늦게 온 연산이 다른 자리에 들어간다. 대신 안정된 묘비를 압축한다 — 내용·기록을 버리고 자리만 남기고, 한 사람이 연달아 친 글자의 묘비는 토큰 하나(▒×N6A)로 합친다. 묶음은 자리 판단에서 원래 글자들과 똑같이 행동한다.

기준점 = min over 참여자 ( 받은 곳 ack ,  되돌리기 핀 − 1 )
  • 받은 곳(ack): 그 뒤에 그 참여자가 보낼 연산은 그 지우기를 이미 본 상태라, 압축된 토큰을 기준으로 삼지 않는다.
  • 되돌리기 핀: 내 되돌리기가 취소할 수 있는 지우기 가운데 가장 이른 것. 그 앞까지만 압축한다.
  • 끊긴 참여자도 2분 동안은 기다린다. 창을 닫으면 바로 빠진다.
  • ack 는 Change 와 같은 줄로 차례로 나간다. 앞질러 가면 아직 안 보낸 연산이 기댄 토큰이 압축될 수 있다.
  • GC 자체도 로그의 한 줄 {serverSeq, gc: 기준점} 이다. 모든 복제본이 같은 자리에서 같은 압축을 한다. 서버는 압축할 묘비가 12개 넘게 모이면 스스로 GC 한다.

대조군 — 규칙을 일부러 빼면 시험이 잡는다

일부러 망가뜨린 것갈린 대본 (참여자 2 / 4)

스키마 주입

CRDT 는 블록 종류를 모른다. 스키마는 SyncClient 를 만들 때 넣는다. 스키마 기반 문서 에디터의 스키마처럼 노드 종류마다 children 으로 트리를 적고, 종류마다 모양 하나와 속성·서식을 정한다. 새 블록 종류를 더할 때 CRDT 코드는 바뀌지 않는다.

모양뜻데모 스키마의 종류
text글을 담는 블록. 흐름 줄에서 표지가 열고 다음 표지까지가 안. children 에 올 수 있는 inline, text:false 면 글자를 받지 않는다paragraph · heading1·2 · quote · list-item · image · caption-paragraph
inlinetext 블록 안에서 글자 한 자리를 차지inline-image
flow블록이 흐르는 줄 하나를 가진 그릇 — Enter 로 나누고 Backspace 로 합치는 곳content · table-cell-body · image-component · callout
group이어진 항목 블록을 묶어 보이는 그릇. 저장하지 않는다list · caption
grid · row · cell표 · 표 행 · 표 칸. 칸의 children 은 칸 안 흐름 그릇 하나. 행·열 수는 정하지 않는다table · table-row · table-cell
atom안이 없는 블록divider
span값 서식이 같은 이어진 글자를 묶어 보이는 것. 저장은 글자마다의 서식inline-hyperlink (서식 link → 속성 url)
 
content ─ paragraph(─ inline-image · inline-hyperlink) · heading1 · heading2 · quote
        ─ list ─ list-item
        ─ table ─ table-row ─ table-cell ─ table-cell-body ─ paragraph · list · image-component
        ─ image-component ─ image ─ inline-image
                          ─ caption ─ caption-paragraph
        ─ callout ─ paragraph · heading2 · list · table · image-component
        ─ divider

글자 서식은 둘이다 — 켜기/끄기 서식(marks: bold·italic·underline·strike)과 값 서식(markValues: link 주소, 꼴은 pattern 으로 검사). 새로 친 글자는 켜기/끄기 서식만 물려받는다.

속성 명세: default, values(허용 값), min·max, pattern(정규식, 색 같은), inherit(Enter 로 나눈 블록이 물려받음), computed(CRDT 가 계산해 내보내는 값 — colspan·rowspan·spanned). 편집기 표시는 ui(label, list, variants, placeholder).

검사는 바뀌지 않는 사실만 본다

서버는 스키마로 "이 줄에 이 종류가 올 수 있나", "이 속성 값이 맞나"를 검사한다. 이때 쓰는 것은 토큰이 어느 줄에 있는지와 노드가 태어날 때 무슨 종류였는지뿐이다. 지금 종류·살았나는 복제본마다 다를 수 있다. 그것으로 거절하면 이미 자기 화면에 적용한 참여자와 서버가 갈라진다.
  • 그래서 검사는 줄 단위다 — "이 줄의 어느 text 종류든 이 inline 을 받으면 통과".
  • 서버가 스키마 없이 돌아도 된다. 순서 매기기·적용·GC 는 똑같고, 검사만 덜 할 뿐이다. 시험으로 확인했다.
  • 무작위 12,000 판(3000 대본 × 참여자 2·4 × GC 끔·켬)에서, 클라이언트가 만든 연산을 서버 검사가 거절한 일은 0 이다 — 거절되면 시험 하네스에서 오류로 잡힌다.

모델 출력

toJSON() 은 스키마의 종류 이름으로 된 트리다. 스키마 기반 문서 에디터의 문서 JSON 과 같은 꼴이라, 나중에 그 에디터와 이을 때 그대로 비교할 수 있다. 저장에서 날것의 트리를 만들고 모양 정리(model.ts 의 canonical — 목록 묶기·속성 기본값·글 조각 합치기·표 칸 맞추기)를 거쳐 나온다. 편집기 쪽 모델도 같은 규칙으로 정리하므로 두 쪽이 같은 꼴이 된다. 표 뒤 빈 자리(글 없는 virtual)는 모델에 없다.

{"type": "content", "children": [
  {"type": "paragraph", "runs": [{"text": "pic ", "marks": {}}, {"type": "inline-image", "attrs": {…}},
    {"type": "inline-hyperlink", "attrs": {"url": "https://example.com"}, "runs": [{"text": "링크", "marks": {}}]}]},
  {"type": "list", "attrs": {"listType": "numbered"}, "children": [
    {"type": "list-item", "attrs": {"level": 0}, "runs": […]}]},
  {"type": "table", "attrs": {"header": false}, "children": [
    {"type": "table-row", "children": [
      {"type": "table-cell", "attrs": {"colspan": 2, "rowspan": 2, "backgroundColor": "#dcfce7"},
       "children": [{"type": "table-cell-body", "children": [{"type": "paragraph", "runs": […]}]}]},
      {"type": "table-cell", "attrs": {"spanned": true}, "children": […]}]}]},
  {"type": "image-component", "children": [
    {"type": "image", "runs": [{"type": "inline-image", "attrs": {"src": "…", "width": 160, "height": 90}}]},
    {"type": "caption", "children": [{"type": "caption-paragraph", "runs": [{"text": "a cat", "marks": {}}]}]}]}]}

블록별 동작

글자 서식

  • 범위가 아니라 글자마다 LWW. 서식 연산은 "내가 본 글자들의 이름표 목록"이라, 그 사이 남이 범위 안에 넣은 글자는 바뀌지 않는다
  • 새 글자는 왼쪽 글자의 서식을 물려받는다 (링크는 빼고)
  • 링크: 글자마다 link 주소(LWW). 모델에서 같은 주소로 이어진 글자를 inline-hyperlink 하나로 묶는다. 동시에 다른 주소를 걸면 나중 쪽
  • 글 안 그림은 건너뛴다

목록 — 평평하게 저장

  • list-item 은 흐름 줄의 text 블록 (listType·level). 모델에서 이어진 것끼리 list 로 묶는다
  • 진짜 그릇으로 저장하면 항목이 들고 날 때마다 블록 옮기기가 된다. 평평하면 종류 바꾸기 하나 — 항목을 빼는 사이 남이 친 글이 그대로 남는다
  • 번호는 화면에서 센다. 스키마 기반 문서 에디터도 목록을 속성으로 든다

이미지 · 캡션

  • image-component 그릇 줄에 image 블록(글자 안 받음, inline-image 하나)과 caption-paragraph 가 이어진다. 캡션도 목록처럼 묶어서 보인다
  • 캡션은 그림 블록에 합쳐지지 않는다 (Backspace·Delete·범위 지우기)
  • 그림 크기 동시 변경은 나중 쪽

상자 · 구분선

  • 상자(callout)는 body 줄 하나를 가진 그릇. 안에 목록·표·이미지
  • 구분선은 atom. 그 뒤 블록 맨 앞 Backspace 로 지운다
  • 상자 색(tone)은 LWW 속성

표

표 노드는 rows 줄(table-row 노드)과 cols 줄(열 노드)을 가진다. 칸은 (행, 열) 이름표 쌍으로 가리키는 자리 줄이고, 그 줄이 table-cell-body 다. 행·열의 수는 스키마가 정하지 않는다 — 넣을 때 고르고 나중에 더하고 뺀다.

동시에 일어난 일결과 (모든 복제본 같음)
A 는 행을, B 는 열을 더함3×3. 서로 모르고 만든 행과 열이 만나는 칸에도 바로 쓸 수 있다
A 는 열을 지우고, B 는 그 열의 칸에 씀열이 사라진다. B 의 글은 안 보이는 칸에 살아 있고, A 가 되돌리면 함께 돌아온다
A 는 표를 지우고, B 는 칸에 씀표가 사라진다. 되돌리면 B 의 글까지 돌아온다
남은 두 행을 둘이 하나씩 지움행이 없는 표는 통째로 안 보인다
칸 안 같은 자리 동시 Enter새 줄 하나 (본문과 같은 규칙)
같은 자리에 표 둘을 넣음둘 다 남고 같은 순서
내가 있던 열을 남이 지움커서는 옆 칸으로

칸 합치기 (colspan · rowspan)

칸에는 토큰이 없으므로 합치기는 표 노드의 속성 $span:왼쪽위행,왼쪽위열 = {끝 행, 끝 열}(이름표, LWW)로 적는다. 모델은 스키마 기반 문서 에디터처럼 full grid 다 — 모든 행에 모든 칸이 있고, 왼쪽 위 칸에 colspan·rowspan, 가려진 칸에 spanned: true.

  • 크기를 개수가 아니라 끝 이름표로 적으므로, 합치는 사이 남이 그 사이에 넣은 열도 함께 덮인다. 끝 열을 지우면 줄어든다.
  • 왼쪽 위 칸의 행·열이 지워지면 합치기는 없어지고 가렸던 칸이 다시 보인다.
  • 겹치는 합치기를 동시에 하면 나중 이름표 것 하나만 받는다.
  • 가려진 칸의 글은 숨을 뿐이고 나누면 다시 보인다. 합칠 때 글을 모으면 복사가 되어, 그 사이 남이 그 칸에 친 글이 갈린다.

칸 배경색

같은 방식으로 표 노드에 $cell:행,열|backgroundColor 로 적는다. 스키마 table-cell 속성 가운데 computed 가 아닌 것만 쓸 수 있고, 색은 #rrggbb 꼴(pattern)만 받는다. 색은 행·열 이름표에 붙어 있어 앞에 행·열이 들어와도 같은 칸에 남고, 열을 지웠다 되돌리면 색도 돌아온다.

편집 API — 모델 연산 다섯 가지

편집기는 CRDT 의 줄·토큰을 모른다. 모델 경로(toJSON 트리의 자식 번호, 스키마 기반 문서 에디터의 숫자 배열 트리 경로와 같은 꼴)와 모델 노드로 말한다. 연산은 그 에디터의 문서 조작 엔진과 같은 이름·뜻의 다섯 가지다.

doc.edit([
    {op: "delete", at: [0], count: 1},                                       // 에디터의 내용 통째 바꾸기 꼴
    {op: "insert", at: [0], content: [{type: "paragraph", runs: [{text: "after", marks: {}}]}]},
]);
doc.edit([0, 1, 2].map(r => ({op: "insert", at: [1, r, 1], content: [{type: "table-cell"}]})));   // 행마다 칸 = 열 하나
doc.edit([{op: "update", at: [1, 0, 0], attrs: {colspan: 2, backgroundColor: "#dcfce7"}}]);
doc.edit([{op: "split", at: [2, 4]}]);                                       // Enter
연산모양에 따라
insert글 안 → 글자·inline · 글 안에 블록 → 그 자리에서 나누고 사이에 · 흐름·목록 → 블록(표면 행·열·칸까지, 칸 합치기·칸 속성 포함) · 표 → 행 · 행 → 열
delete글자 · 블록(통째) · 행 · 열 · 마지막 행·열이면 표째로
update블록 종류(type)·속성 · 목록 노드면 그 항목 모두 · 글 범위(length)면 서식 · 칸이면 칸 속성·colspan·rowspan
splitEnter — 경계 키는 컴파일하는 순간의 왼쪽·오른쪽 토큰. 스키마의 next·inherit
merge앞 글 블록에 합치기 = 표지 지우기. 앞이 글자를 받지 않는 블록이면 하지 않는다

묶음 안의 기억 두 가지

  • 비운 머리 — 흐름의 첫 블록을 지우면 줄 머리(언제나 첫 블록)는 남지만 빈 자리가 된다. 같은 묶음의 다음 경로는 그 자리를 세지 않고, 맨 앞에 글 블록이 오면 채운다. 끝까지 비어 있으면 다음 글 블록을 당겨 온다. 그래서 스키마 기반 문서 에디터의 "지우고 다시 넣기"가 그대로 맞는다.
  • 열 접기 — 스키마 기반 문서 에디터의 트리에는 열이 없어서 열 넣기·지우기가 "행마다 같은 번호의 칸"으로 온다. 같은 표·같은 칸 번호로 이어지는 것을 열 노드 하나로 접는다. 한 행에만 와도 열 하나로 바로잡는다.

normalize — 편집기에 알릴 차이

edit() 은 만든 전선 연산과 함께 normalize 를 돌려준다. 편집기가 이 묶음을 자기 모델에 그대로 적용한 결과와 CRDT 모델이 다르면, 그 차이를 메우는 연산이다. 보통은 비어 있다.

생기는 경우왜
한 행에만 칸 넣기열 하나로 바로잡는다 — 다른 행에 빈 칸
합친 칸 사이에 열·행 넣기합치기 끝을 이름표로 적으므로 새 열도 덮인다 (편집기는 colspan 을 그대로 둔다)
겹치는 칸 합치기나중 것 하나만 받는다
글자가 있는 빈 자리 앞의 표 지우기빈 자리 글이 앞 블록에 붙는다 (동시편집에서만 생긴다)

무작위 3000 대본 판마다 normalize 가 붙은 내 편집은 8~9번이었고, 모두 위의 경우였다.

옛 편집 함수에서 옮기기

편집 함수 18개(insertText, splitBlock, insertAxis, setSpan …)를 commands.ts 의 명령으로 옮겼다. 명령은 사람의 행위를 모델 연산으로 바꿀 뿐이다. 같은 상태에서 옛 함수와 새 명령을 나란히 돌려 모델을 비교했고(1000 대본 × 40걸음), 34,001걸음에서 차이 0 을 확인한 뒤 옛 함수를 지웠다. 한 번 나온 차이(칸 합치기의 "이미 같은 값" 판정)는 고쳤다.

받는 쪽 이벤트

client.onModelEvents = (events, info) => … — 남의 변경·되돌리기·스냅숏으로 모델이 바뀌면, 앞 모델을 뒤 모델로 바꾸는 모델 연산을 준다. 편집기는 이것을 자기 모델에 적용하면 된다.

  • 받기 전·후 모델을 비교해 만든다. 바뀐 곳만 — 글자 하나면 글자 하나 넣기, 열 하나면 행마다 칸 넣기(스키마 기반 문서 에디터의 연산 꼴), 칸 색이면 칸 update.
  • 흐름은 펼친 항목 줄에서 비교하고, 연산을 하나 만들 때마다 작업 사본에 적용해 다음 경로를 그 사본에서 구한다. 처음엔 목록 묶음 단위로 비교했다가, 넣은 목록이 옆 목록과 바로 붙어 다음 경로가 어긋나는 것을 거울 시험이 잡았다.
  • 내보내기 전에 앞 모델에 적용해 검산하고, 틀리면 문서 통째 바꾸기로 물러선다 (info.fallback). 무작위 3000 대본에서 물러선 일은 0.
  • 처음 제안은 "전선 연산을 하나씩 번역"이었다. 모델 비교로 바꾼 까닭: 세밀함은 같고, 흡수된 표지·빈 자리·가려진 칸처럼 보이는 변화가 없는 경우를 따로 다룰 필요가 없어 언제나 맞는다.

거울 시험

무작위 시험에서 참여자마다 "편집기 쪽 모델"(스키마 기반 문서 에디터 자리)을 따로 둔다. 이 거울은 내 편집 연산 + normalize, 그리고 받는 쪽 이벤트로만 바뀐다. 매번 CRDT 모델과 같은지 본다.

커서와 선택

모델 경로토큰 키
꼴[블록, …, 글자 자리] — 스키마 기반 문서 에디터의 selection start·end 와 같은 꼴"이 토큰 바로 뒤" — 12@A-x8f2
쓰는 쪽편집기CRDT
남이 편집하면흔들린다 — 앞에 글이 들어오면 번호가 바뀐다안 흔들린다
  • 커서·선택의 시작·끝은 토큰 키로 들고 있다가 그릴 때 경로로 바꾼다 — anchorAt(doc, 경로) → 키, pathAt(doc, 키) → 지금 경로.
  • 편집기 쪽 순서: 선택이 바뀔 때(또는 받기 직전에) 키를 잡아 둔다 → 받는 쪽 이벤트를 적용한다 → 키로 선택을 되돌린다.
  • 그 글자가 지워졌으면 왼쪽으로 가장 가까운 자리, 그 칸이 안 보이게 됐으면 옆 칸, 합친 칸에 가려졌으면 왼쪽 위 칸으로 나온다.
  • 둘 다 왼쪽 토큰에 붙이므로, 내 커서 자리에 남이 친 글은 커서 오른쪽에 생긴다. 선택의 시작 자리에 들어온 글은 선택 안으로, 끝 자리에 들어온 글은 선택 밖으로 간다.
  • 남의 커서(presence)는 처음부터 토큰 키로 주고받는다.
  • 시험: "cdef" 를 선택해 둔 사이 남이 앞에 글을 넣고 블록을 나눠도, 되돌린 선택이 그대로 "cdef" 를 감싼다.

ProseMirror 연동

편집 API 가 편집기를 모르므로 ProseMirror 도 같은 길로 붙는다. /pm 에서 데모 편집기(A)와 ProseMirror(P)가 같은 문서를 함께 편집한다.

부분하는 일
스키마 (pm/schema.ts)우리 스키마에서 ProseMirror 스키마를 뽑는다. 목록은 평평하다 — list_item 은 listType·level 속성을 가진 textblock (prosemirror-schema-list 의 그릇 목록이면 항목이 들고 날 때 노드 옮기기가 된다). 표는 prosemirror-tables 꼴, 링크는 값 하나짜리 mark
변환 (pm/convert.ts)모델 ↔ ProseMirror 문서, 모델 경로 ↔ ProseMirror 위치. 우리 표는 full grid, ProseMirror 표는 가려진 칸이 없다 — 변환이 넣고 뺀다. 가려진 칸의 숨은 글은 바꾸기 전 모델에서 가져와 잃지 않는다
보내는 쪽 (pm/binding.ts)Step 을 하나씩 모델 연산으로. 한 블록 안 글 → insert·delete, Enter(splitBlock) → split, 블록 맨 앞 Backspace(join) → merge, 블록 걸친 지우기, 서식 → update. 나머지(종류 바꾸기·표 행/열·붙여 넣기)는 Step 앞·뒤 모델 비교로 — prosemirror-tables 의 열 넣기는 행마다 칸 넣기가 되어 CRDT 가 열 하나로 접는다
받는 쪽남의 변경·되돌리기 → 새 문서와의 차이 구간만 바꾸는 transaction 하나. 내 커서는 ProseMirror 가 그 Step 을 따라 옮기고, 남의 커서는 토큰 키 → 경로 → 위치로 장식을 그린다
되돌리기ProseMirror history 대신 CRDT 의 참여자별 되돌리기
y-prosemirror 와 다른 점 — Enter 를 문서 차이(앞 문단 줄이기 + 뒷글 다시 넣기)가 아니라 split 하나로 보낸다. 그래서 A 가 나누는 사이 B 가 뒷부분에 친 글자가 그대로 남고, 같은 자리 동시 Enter 는 새 줄 하나다. 둘 다 시험이 있다.

무작위 시험 — 진짜 ProseMirror 명령으로

다음 단계로 생각해 볼 것

  1. 에디터 어댑터. 스키마 기반 문서 에디터의 연산 ↔ 모델 연산 변환 — inline-text 경로를 글자 자리로, 두 단계 Enter 를 하나로, 목록 표현 맞추기. 실제 그 에디터(jsdom) 하네스로 3000 대본 거울 시험.
  2. ProseMirror 다듬기. 한글 조합 중 같은 문단 동시 편집을 실제 브라우저에서 더 보기, 합치기·붙여 넣기도 뜻을 살려 옮기기, 칸 여러 개 선택.
  3. 칸 여러 개 선택과 스키마의 min·max.
