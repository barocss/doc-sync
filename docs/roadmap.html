doc-sync · 2026-10-22

@barocss/doc-sync 로드맵

문서에 특화된 CRDT 시제품을 스키마 기반 문서 에디터의 실제 동시편집에 쓸 수 있는 것으로 만드는 길. 가장 큰 불확실성(성능)을 맨 먼저 재고, 그 결과로 나머지 길을 확정한다.

단계 8개 (0~7) 결정 지점 5곳 1인 기준 어림 20~27주 · 2인이면 12~16주 첫 결정: 단계 0 끝 (1주 뒤)

요약

  • 먼저 잰다. 같은 편집 대본으로 Yjs·Yorkie 와 시간·메모리·전송량을 비교한다(단계 0). 격차가 데이터 구조로 메울 수 있는 크기인지가 첫 결정이다.
  • 그다음 빠르게. 위치 색인, 줄 단위 증분 계산, 받는 쪽 비교 좁히기(단계 1). 연속 글자 묶기는 구현 제외, 이진 형식은 결정 대기다. 기존 동시편집 규칙을 유지하며 측정한 병목부터 줄인다.
  • 같이 단단하게. 연산 명세와 성질 시험(단계 2), 서버 스냅숏·로그 압축·WebSocket·샤딩(단계 3)은 성능과 나란히 간다.
  • 스키마가 바뀌어도 문서가 산다. 판 번호와 이전 규칙(단계 4) — 스키마를 주입하는 방식이라 꼭 필요하다.
  • 스키마 기반 문서 에디터에 붙인다. 에디터 연산 ↔ 모델 연산 어댑터, 실제 에디터로 3000 대본 거울 시험(단계 5). 여기가 이 로드맵의 목적지다.
  • 기능 채우기(단계 6)와 배포 준비(단계 7) 뒤에 사내 시범 운영으로 정식 판을 정한다.

2026-10-23 실행 현황: 단일 공개 패키지 구성을 유지하며, 기준 측정 확대·한 글 블록 수신 비교·큰 문자열 캐시 처리·Unicode undo·명세와 장기 CI 기반을 추가했다. 아래 계획의 전체 종료 조건이 충족된 것은 아니다. 최신 범위와 남은 조건은 실행 현황을 본다. 과거 결과와 제안값은 그 시점의 기록이다.

자리 색인은 토큰마다 마지막 자리를 기억하고 맞춰 보는 방식으로, 블록 목록은 글자 연산이면 그 블록만 고쳐 쓰는 방식으로 바꿨다. 동작은 그대로다 — 시험 83개와 무작위 3000 대본(블록 검산 켬) 모두 통과. 당시 프로파일의 남은 비용은 나누기·합치기 전체 재계산 약 50%, 평평한 배열 끼워 넣기 복사 약 28%였다. 현재 소스의 비율은 다시 측정해야 한다. 메모리·저장 크기(글자마다 토큰)도 남아 있다.

아래는 처음 잰 값에 대한 메모다. 세 결과(로컬·받는 쪽·저장 뒤 불러오기)는 모두 맞다. 1만 자 → 10만 자에서 로컬 p50 이 약 25배 — 편집 하나가 O(n) 이상이다. 프로파일: 줄의 자리 색인을 토큰을 넣을 때마다 버리고 다시 만드는 것이 44%, 블록 목록을 편집마다 처음부터 다시 계산하는 것이 32%. 둘 다 구조의 한계가 아니라 알고리즘 문제라, 이 둘을 먼저 고치고 다시 잰 뒤 G0 를 내리는 쪽을 제안한다. 남은 대본: 참여자 4명 동시편집, 50×10 표, 편집 1만 번 뒤 열기, Yorkie 비교.

단계 3 · 저장·운영 3~4주 · 1 과 나란히

  • 스냅숏 + 로그 압축 — GC 기준점에서 서버 스냅숏을 저장하고 그 앞 로그를 잘라낸다. 재시작은 스냅숏 + 로그 꼬리
  • WebSocket — SSE 를 바꾼다. 재연결, 백프레셔, 연결당 묶어 보내기
  • 문서 단위 샤딩 — 한 문서는 한 서버 프로세스가 맡는다(서버 순서 = 인과 순서이므로). 라우팅, 장애 조치(스냅숏 + 로그 꼬리로 다른 프로세스가 이어받기)
  • 인증·권한 훅 — 쓰기·읽기 전용 참여자, 문서 권한은 바깥 시스템에 묻는다
  • 제한 — 변경 크기, 문서 크기, 참여자당 초당 연산 수 (DoS)
  • 관측 — GC 기준점 지연, 묘비 수, 문서 크기, 연결 수, 검사 거절 수

끝 조건

단계 4 · 스키마 진화 2주

스키마를 바깥에서 주입하므로, 스키마가 바뀌는 날 저장된 문서가 어떻게 되는지를 먼저 정해야 한다.

  • 문서에 스키마 판 번호와 지문을 둔다. 접속할 때 클라이언트·서버가 맞춰 본다
  • 저장 스키마와 보기 스키마를 나눈다 — 문서에 저장된 스키마(서버 검사의 기준)와 클라이언트가 가진 스키마를 따로 둔다. 접속 때 둘을 견줘 볼 수 있음 · 올릴 수 있음 · 같음을 정하고, 클라이언트 스키마가 저장 스키마를 넓히기만 했으면 저장 스키마를 올린다
  • 더하기는 그대로 — 종류·속성 추가, children 넓히기, 새 서식. 옛 문서가 새 스키마를 이미 만족한다
  • 빼기·좁히기·이름 바꾸기는 이전 함수로 — 모델 → 모델 함수(편집 API 로 적용)를 서버가 판 경계에서 한 번 돌린다. 옛 판 클라이언트는 새로 불러오게 한다
  • 저장된 문서 묶음이 새 스키마를 만족하는지 보는 일괄 검사 도구

끝 조건

이전 시험(옛 판 문서 묶음 → 새 판) 통과, 옛 판 클라이언트가 새 문서를 망치지 못함 (서버가 판으로 거절).

단계 5 · 스키마 기반 문서 에디터 연동 4~6주

이 로드맵의 목적지. ProseMirror 연동에서 쓴 짜임을 스키마 기반 문서 에디터에 옮긴다.

  • 에디터 어댑터 — 에디터 연산(insert·delete·update·split·merge) ↔ 모델 연산
    • inline-text 경로를 글자 자리로 접기, 두 단계로 오는 Enter(split [0,0,5]·split [0,1])를 하나로 접기
    • 목록: 에디터의 문단 + listGroupId·listItemLevel ↔ list-item + listType·level
    • 맨 앞 빈 문단(흐름은 글 블록으로 시작), 가려진 칸(full grid)을 맞추기
  • 플러그인 모양 — 앞선 Yorkie 실험의 동시편집 플러그인처럼 에디터에 붙인다. 백엔드만 바꿔 끼우게
  • 시험 — 실제 스키마 기반 문서 에디터(jsdom) 하네스로 3000 대본 거울 시험, 앞선 Yorkie 시제품의 브라우저 시나리오 27개 재사용, 실브라우저 한글 조합

스키마 이전이 문서를 망친다중간이전은 서버에서만, 이전 전 스냅숏 보존·되돌리기, 일괄 검사 도구

지식이 한 사람에게 몰린다중간명세(단계 2)와 시험이 지식을 옮긴다. 2인 이상이 단계 1·3 을 나눠 맡는다

기간은 1인 기준 어림이다. 단계 0 결과와 G2(서버 운영 모델)에 따라 크게 달라진다 — G2 가 "Yorkie 위"로 가면 단계 3 이 크게 준다.

  2. 2주차 — G0 가 "예"면 현재 프로파일 1순위부터. 연속 글자 묶기는 구현 제외다. 나란히 명세서 초안(상태·전선 연산 5개)

하지 않을 것

  • 서버 없는 P2P 동기화 — 서버 순서가 인과 순서라는 단순함을 지킨다
  • 범용 JSON CRDT — 문서 모양에 특화된 것이 강점이다
  • 임의 트리 옮기기를 기본 연산으로 — 필요하면 단계 6 에서 따로 정한다
  • 몇 주씩 끊긴 채 쓰는 오프라인 우선 — lease 를 넘긴 참여자는 스냅숏부터 다시 받는다
