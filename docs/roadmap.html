doc-sync · 2026-10-22

@barocss/doc-sync Roadmap

A path from a document-specific CRDT prototype to practical collaboration in a schema-based document editor. Measure the largest uncertainty, performance, first. Use the results to confirm the remaining path.

8 stages (0–7) 5 decision gates Estimated 20–27 weeks for one person · 12–16 for two First decision: end of stage 0 (after 1 week)

Summary

  • Measure first. Compare time, memory, and transport volume with Yjs/Yorkie using the same editing scripts (stage 0). The first decision is whether data-structure changes can close the gap.
  • Then improve speed. Position indexes, line-level incremental calculation, and narrower receiving comparisons (stage 1). Consecutive-character grouping is excluded from implementation; binary encoding awaits a decision. Reduce measured bottlenecks while retaining existing collaboration rules.
  • Improve reliability in parallel. Operation specifications/property tests (stage 2) and server snapshots/log compaction/WebSocket/sharding (stage 3) proceed alongside performance work.
  • Preserve documents through schema changes. Versions and migration rules (stage 4) are necessary for an injected-schema design.
  • Integrate the schema-based document editor. Editor operations ↔ model operations, tested by 3000 mirror scripts with the real editor (stage 5). This is the roadmap's destination.
  • Feature completion (stage 6) and release preparation (stage 7) lead to an internal pilot that determines the production release.

Execution status, 2026-10-23: retained the single public package and added expanded baseline measurements, single-text-block receiving comparison, large-string cache handling, Unicode undo, specifications, and long-run CI foundations. The full exit conditions below are not met. See execution status for the latest scope and remaining conditions. Historical results and proposed values describe their recorded date.

Stage Overview

Stage 0 · Baseline Measurement 1 week

Why first: performance is this design's largest uncertainty. A large deficit requires revisiting data structures, so measure before other work.

Tasks

  • Measurement harness benchmarks/: run the same scripts on three implementations: this library, Yjs with a y-prosemirror-shaped document, and Yorkie Tree using the earlier Yorkie experiment plugin's conversion.
  • Five scripts: one user typing 10,000 characters; 100,000-character paste; 4 participants collaborating for 30 minutes (random scripts at real-time pace); 50×10 table editing; opening after 10,000 edits.
  • Metrics: local-edit latency p50/p95, remote-application latency, memory, snapshot size, wire bytes per operation, opening time, model calculation (toJSON), and receiving-comparison cost.
  • Profile where time is spent: per-character tokens, full recomputation, comparison, and other costs.

The following note describes the initial measurements. All three results (local, receiving, save/reload) are correct. Moving from 10,000 to 100,000 characters increased local p50 about 25×, implying O(n) or greater per edit. Profiling found 44% in discarding/rebuilding line-position indexes for each insertion and 32% in rebuilding block lists for every edit. Both are algorithm issues rather than structural limits. The proposal is to fix both, remeasure, then decide G0. Remaining scripts: 4-participant collaboration, 50×10 tables, opening after 10,000 edits, and Yorkie comparison.

Stage 2 · Correctness Specification 2 weeks · parallel with 1

  • Specification, docs/spec.md: state (lines, tokens, records), application rules for the 5 wire operations, model function (blocks, groups, tables, virtual positions), GC rules, and validation from immutable facts.
  • Property tests: commutation of independent operations, duplicate-operation idempotence, delayed causal arrival, model independence from GC timing, and no tombstones in the model.
  • Long random runs: nightly CI with one million operations and 8 participants, including lease expiry, snapshot reconnection, and server restart.
  • Long-disconnected participants: discard history after lease expiry and reconnect from a snapshot. This is a known current gap.

Exit Conditions

Specification review passes; property tests and long random CI runs show 0 divergences for two consecutive weeks.

Stage 3 · Storage and Operations 3–4 weeks · parallel with 1

  • Snapshots + log compaction: persist server snapshots at GC frontiers and truncate earlier logs. Restart from a snapshot + log tail.
  • WebSocket: replace SSE. Add reconnection, backpressure, and per-connection batching.
  • Document sharding: one server process owns each document because server order equals causal order. Add routing and failover to another process using snapshot + log tail.
  • Authentication/authorization hooks: writable and read-only participants; consult the external system for document permissions.
  • Limits: change size, document size, and operations per second per participant (DoS).
  • Observability: GC-frontier lag, tombstone count, document size, connection count, and validation rejections.

Exit Conditions

No data loss under fault injection (forced process termination, network interruption), log size stabilizes in proportion to document size, and documents run across two servers.

Stage 4 · Schema Evolution 2 weeks

Because schemas are injected externally, define what happens to stored documents when schemas change.

  • Store schema version and fingerprint in the document. Client and server compare them at connection.
  • Separate stored and view schemas. The persisted schema governs server validation; clients have their own schema. Compare them at connection to determine can view, can upgrade, equivalent. Upgrade the stored schema if the client schema only widens it.
  • Additive changes need no migration: new types/attributes, wider children, new marks. Existing documents already satisfy the new schema.
  • Removal, narrowing, and renaming use migration functions: the server runs a model → model function once at the version boundary through the edit API. Old-version clients must reload.
  • Provide a batch validator to check stored-document collections against the new schema.

Exit Conditions

Migration tests pass for old-version document collections. Old clients cannot corrupt new documents because the server rejects incompatible versions.

Reference: Fluid Framework SharedTree solves the same problem by separating stored and view schemas, only widening stored schemas, and checking compatibility through canView, canUpgrade, and isEquivalent. Its central service also defines order, making the approach directly applicable. Schema Evolution · SchemaCompatibilityStatus

Stage 5 · Schema-Based Document Editor Integration 4–6 weeks

The roadmap's destination. Transfer the structure used in ProseMirror integration to the schema-based document editor.

  • Editor adapter: editor operations (insert/delete/update/split/merge) ↔ model operations
    • Fold inline-text paths to character positions and two-stage Enter (split [0,0,5]/split [0,1]) into one split.
    • Lists: editor paragraph + listGroupId/listItemLevel ↔ list-item + listType/level.
    • Align leading empty paragraphs (flows start with text blocks) and hidden cells (full grid).
  • Plugin structure: attach to the editor like the earlier Yorkie collaboration plugin, allowing backend replacement.
  • Tests: 3000 mirror scripts with the real schema-based document editor in jsdom, reuse 27 browser scenarios from the earlier Yorkie prototype, and real-browser Korean composition.

Exit Conditions

Real schema-based document editor operations produce 0 mirror mismatches; all intent scenarios pass; 0 broken Korean compositions; stage 1 performance targets also hold inside the editor.

Stage 7 · Release Preparation 2–3 weeks

  • Package structure: per user decision, one public @barocss/doc-sync package and private demo/benchmarks. crdt, sync, server, and pm are internal layers and export paths. Define API stability and version policy before release.
  • Documentation: specification, API, schema guide, operations guide.
  • Security review: stronger validation, limit values, malformed-operation fuzzing.
  • Migration tools: Yorkie Tree documents → this model. Since the model matches a schema-based document editor, migrate through model insert operations.
  • Two-week internal pilot: evaluate metrics and incidents for G4.

The Next Two Weeks

  1. Week 1: measurement harness and five scripts. Start with this library and Yjs (from npm). Attach Yorkie Tree using the earlier experiment plugin's conversion. Result tables + profiles → G0.
  2. Week 2: if G0 is yes, start with the top current profiling bottleneck. Consecutive-character grouping is excluded from implementation. In parallel, draft the specification (state + 5 wire operations).

Non-Goals

  • Serverless P2P synchronization: preserve the simplicity of server order as causal order.
  • General-purpose JSON CRDT: document-specific shapes are the strength.
  • Arbitrary tree moves as a primitive operation: decide separately in stage 6 if needed.
  • Offline-first use while disconnected for weeks: participants beyond their lease restart from snapshots.
