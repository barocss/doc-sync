# 연속 문자열 CRDT 저장 검토

- work_id: other-editors-100k-20261022
- 상태: 설계 검토. 저장 구조 변경과 성능 개선은 아직 검증하지 않았다.
- 기준: 2026-10-22의 현재 작업 트리. 비교 시험의 `source-manifest.json`에 소스 해시를 기록했다.
- 관련 결과: [다른 편집기 비교](../../benchmarks/results/monorepo-2026-10-22/other-editors-100k/report.md).

## 결정 제안

**논리 ID는 유지하고, 메모리에는 연속 문자열 묶음을 저장한다.** 묶음 내부를 편집할 때 필요한 경계만 나눈다. 묶음의 물리 주소를 커서나 원격 연산에 사용하지 않는다.

한 글자씩 타이핑한 입력도 합칠 수 있어야 한다. 여러 글자를 한 번에 넣은 입력만 합치는 방식은 부족하다. 타이핑, IME 확정, 붙여넣기는 입력 단위가 다르다. 저장 묶음과 전송 묶음, undo 묶음도 각각 다르다.

## 현재 코드에서 확인한 사실

| 계층 | 현재 동작 | 근거 |
| --- | --- | --- |
| 모델 | 같은 서식의 문자는 `Run.text` 문자열로 표현한다 | `crdt/model.ts`의 `unitsToRuns`, `canonical` |
| 편집 연산 생성 | 같은 서식의 연속 문자를 하나의 `text` 연산으로 만든다 | `crdt/edit.ts`의 `emitUnits` |
| 전송 | `Op.text`는 여러 문자를 담는다. ID는 시작 ID부터 연속으로 배정한다 | `crdt/doc.ts`의 `Op` |
| 메모리 저장 | `apply(text)`가 `text.length`만큼 반복한다. UTF-16 코드 단위마다 `Item`을 만든다 | `crdt/doc.ts`의 `apply` |
| ID 조회 | 글자마다 `byKey` 항목을 둔다 | `crdt/doc.ts`의 `integrate`, `fromSnapshot` |
| 블록과 위치 | `TextBlock.chars`, `BlockCache.of`, `posCache`도 글자별 항목을 사용한다 | `crdt/doc.ts`의 `blocks`, `replaceBlock`, 위치 함수 |
| 삭제 후 압축 | 안정된 연속 묘비는 `span`으로 합친다. 내부 ID의 `byKey` 항목은 남긴다 | `crdt/doc.ts`의 `compact` |
| 스냅숏 | 연속 ID와 origin 표기를 생략하지만, 살아 있는 글자는 각각 기록한다 | `crdt/doc.ts`의 `itemToJSON` |
| undo | 입력 묶음은 이미 시간과 커서로 합칠 수 있다. 대상 ID 목록은 별도로 보관한다 | `crdt/history.ts`의 `record`, `ExistenceStep` |

따라서 문자열 전송은 이미 지원한다. 주요 검토 대상은 **살아 있는 문자열의 메모리 저장과 인덱스**다. 스냅숏 크기와 대량 삭제 전송 크기는 별도 단계가 필요하다.

현재 10만 자 시험은 문단마다 160자를 하나의 모델 문자열로 넣는다. 625개 문단이다. 저장 단계에서 이 문자열을 문자 항목으로 나눈다. 초기 입력을 모든 글자에 대한 별도 편집 호출로 만든 것은 아니다. 측정 중 추가 입력은 한 글자씩이다.

## 제안한 저장 단위

다음은 개념 자료형이다. 구현 API가 아니다.

```ts
type TextSegment = {
  line: LineId;
  actor: string;
  firstLamport: number;
  lengthUTF16: number;
  text: string;                 // 살아 있는 내용. 안정된 묘비는 비울 수 있다.
  firstOrigin: Ticket;
  marks: MarkState;
  deletions: DeletionState;
  compact: boolean;
};
```

오프셋 `i`의 논리 ID는 `{actor, lamport: firstLamport + i}`다. 첫 문자의 origin은 `firstOrigin`이다. 이후 문자의 origin은 같은 actor의 바로 전 논리 ID다. 물리 묶음을 나누거나 합쳐도 이 값은 바뀌지 않는다.

노드와 줄 머리는 별도 항목으로 둔다. 본문, 상자 내부, 표의 각 자리 줄은 지금처럼 구분한다. 다른 줄이나 노드 표지를 가로질러 문자열을 합치지 않는다.

### 나누기와 합치기

예를 들어 `abcd`의 ID가 `A:10..13`이면 한 묶음으로 저장할 수 있다. `b` 뒤에 `X`를 넣으면 저장 순서는 `ab | X | cd`가 된다. 기존 ID는 그대로다. `c`의 origin도 원래 `b`의 ID를 유지한다. 물리적으로 앞에 있는 `X`로 바꾸지 않는다.

묶음은 다음 경계에서 나눈다.

- 내부 ID를 기준으로 삽입할 때
- 삭제·삭제 취소·서식 변경의 시작과 끝
- 노드 표지, 줄, inline 노드의 경계
- 저장 정책에서 정한 최대 묶음 길이

인접한 두 묶음은 다음 조건을 모두 만족할 때 합친다.

- 같은 줄, 같은 actor이고 ID 구간이 연속이다.
- 뒤 묶음의 첫 origin이 앞 묶음의 마지막 논리 ID다.
- RGA 순서에서 두 묶음 사이에 다른 항목이 없다.
- 삭제 집합, 취소 집합, GC 상태와 서식의 **의미**가 같다.
- 합쳐도 최대 묶음 길이를 넘지 않는다.

서식 값만 같다고 합치면 안 된다. LWW의 작성 ID도 보존해야 한다. 생성 시 서식의 작성 ID는 문자마다 다를 수 있다. 이 경우 `구간 시작 ID + 오프셋` 규칙으로 작성 ID를 계산하거나, 별도 서식 구간을 둔다. 같은 서식처럼 보이는 두 문자가 서로 다른 undo 판정을 받을 수 있다.

타이핑 호출 사이에 원격 시계를 관찰하면 ID 번호가 건너뛸 수 있다. 이 경우 무리하게 합치지 않는다. 나중에 더 높은 압축률이 필요하면 복수 ID 구간을 담는 상위 문자열 조각을 별도로 검토한다.

## 필요한 인덱스와 API 변경

`Item.ch`에 긴 문자열만 넣으면 충분하지 않다. 다음 경로도 함께 바꿔야 한다.

| 현재 경로 | 제안 |
| --- | --- |
| `byKey: Map<string, Item>` | actor별 ID 구간 인덱스. 조회 결과는 `{segment, offset}` |
| `Line.items`의 글자 배열 | 노드와 문자열 묶음의 순서 인덱스. 보이는 길이와 전체 길이를 집계 |
| `TextBlock.chars`와 `BlockCache.of` | 블록 안 문자열·inline 구간. 글자별 영구 배열과 역방향 Map 제거 |
| `posCache` | 구간 길이 합계로 위치 ↔ 논리 ID 변환 |
| `rawBlock` / `toJSON` | 문자 객체로 펼치지 않고 서식 구간에서 직접 `Run` 생성 |
| `charsBetween` | 논리 ID 구간 또는 구간 반복자 반환 |
| `History` | 내부 대상은 ID 구간으로 보관. 처음에는 기존 wire ID 배열로 내보냄 |
| 데모의 글자별 DOM 접근 | 문자열·서식 구간과 선택 경계로 렌더링. ID와 offset 조회는 별도 함수 사용 |

균형 트리와 actor별 구간 인덱스가 후보이다. 탐색 목표는 `O(log S)`다. `S`는 저장 묶음 수다. 실제 비용은 분할, 문자열 복사, 서식 경계 수에도 영향을 받는다. 성능 보장은 아직 없다.

기존 `Item[]`을 만들어 두고 새 인덱스를 추가하면 메모리가 두 벌이 된다. 호환용 문자 뷰는 요청한 위치에서만 잠깐 만들어야 한다. 전체 문자 배열을 캐시에 남기는 방식은 피한다. `items`, `lines`, `get`, `TextBlock.chars`를 사용하는 테스트와 UI도 전환 범위에 포함한다.

`Item`, `Line`, `TextBlock`은 현재 패키지에서 export한다. 따라서 이 변경은 내부 자료구조 교체만으로 끝나지 않는다. 소비자 API의 호환 범위와 전환 시점을 명시해야 한다. `Doc.edit`, 모델, wire 형식의 호환성과 자료구조 API의 호환성을 구분한다.

묶음 최대 길이는 256/1024/4096 UTF-16 단위를 후보로 측정한다. 아직 기본값을 정하지 않는다. 짧으면 관리 항목이 늘고, 길면 부분 편집과 복사의 비용이 늘 수 있다. JS 엔진의 문자열 공유를 가정하지 않는다. 작은 문자열 조각이 큰 원본을 붙잡는 메모리도 확인한다.

## 기존 동작을 지키는 조건

| 동작 | 반드시 지킬 조건 |
| --- | --- |
| 동시 삽입 | 내부 origin과 ID 비교를 사용한다. 첫 ID만 비교해 묶음 전체를 건너뛰면 안 된다. 내부 삽입 위치와 충돌 경계에서 나눈다 |
| 부분 삭제 | 대상 ID 구간만 지운다. 동시에 삽입된 다른 actor의 문자는 포함하지 않는다 |
| 삭제 취소 | 지정한 삭제 ID만 취소한다. 다른 삭제가 남으면 계속 숨긴다 |
| 서식과 undo | 값뿐 아니라 LWW 작성 ID와 이전 값을 구간별로 보존한다 |
| 커서와 selection | `Presence.anchor/focus`의 논리 토큰 키를 유지한다. 정방향·역방향·접힌 선택과 경계의 기존 규칙을 유지한다 |
| Enter와 문단 합치기 | 노드 표지와 boundary 규칙을 유지한다. 문자열 분할은 문단 분할과 다르다 |
| GC | 서버 frontier와 undo pin을 그대로 적용한다. 내부 ID와 origin의 순서 의미를 잃지 않는다 |
| 재전송 | 같은 text 연산을 다시 받아도 결과가 같다. 부분적으로 이미 있는 ID 구간도 처리한다 |
| 재연결 | 오래된 로그와 스냅숏을 읽은 뒤 새 묶음으로 구성할 수 있어야 한다 |
| Unicode | wire ID 증가 단위인 UTF-16을 유지한다. 모델 경로의 코드 포인트 변환, 네이티브 UTF-16 위치, 사용자 커서의 grapheme 경계를 구분한다 |

이모지, 결합 문자, ZWJ 문자열, 한글 조합을 포함한다. 저장 경계가 화면의 글자 경계와 같다고 가정하지 않는다. 현재 ID를 코드 포인트나 grapheme 번호로 다시 부여하는 변경은 이번 저장 설계에서 제외한다.

## 호환성과 순서

1. **저장만 변경한다.** `Op.text`, 개별 논리 ID, 기존 JSONL 로그를 유지한다. 서버와 클라이언트가 같은 구간 조회 규칙을 사용한다. 스냅숏은 처음에는 기존 형식으로 내보낸다. 이 단계는 스냅숏 크기 감소를 약속하지 않는다.
2. **중요 소비 경로를 옮긴다.** 블록, 위치, 모델 변환, history, PM과 데모가 구간을 직접 사용하게 한다. 전체 문자 객체 배열을 남기지 않는다.
3. **동작을 대조한다.** 기존 문자 저장 구현을 참조 구현으로 고정한다. 같은 연산과 인과 순서의 여러 수신 순서를 적용해 모델, 논리 ID 순서, 커서, undo, GC 결과를 대조한다. 서로 다른 물리 묶음 모양은 허용한다.
4. **저장 형식을 별도로 바꾼다.** 구간 스냅숏과 del/set ID 구간 전송을 검토한다. 현재 프로토콜에는 기능 협상이 없다. 버전·기능 협상과 구형 판독 경로를 먼저 설계한다. 새 구간 필드를 기존 `span` 필드에 임의로 끼워 넣지 않는다.

전송 변경을 함께 하면 저장 개선과 전송 개선의 원인을 구분하기 어렵다. 첫 비교에서는 같은 논리 연산을 사용한다. 입력을 모으기 위해 전송을 지연시키는 변경도 별도 시험으로 다룬다.

현재 측정은 변경 전 기준값이다. 아래 표의 문자열 묶음 시험은 아직 실행하지 않았다.

| 구분 | 조건과 확인 항목 |
| --- | --- |
| 입력 묶음 | 1자, 10자, 100자, 1000자 삽입을 분리. 같은 총 글자 수와 같은 호출 수 비교를 각각 기록 |
| 실제 타이핑 | 글자별 키 이벤트를 연속 발생. 30/100ms 간격 후보. 로컬 표시와 원격 표시, 큐 누적과 마지막 글자 도착을 기록 |
| IME / 붙여넣기 | IME 확정 문자열과 여러 글자 삽입을 별도 시나리오로 구분. CDP 합성 조합과 실제 OS IME를 구분 |
| 문서 모양 | 10만 자·625문단 외에 10만 자·단일 문단, 작은 run이 많은 문서, 서식이 자주 바뀐 문서 |
| 편집 분포 | 문서 처음·중간·끝, 순차·무작위 삽입, 묶음 내부 삭제와 서식, 반복 나누기·합치기 |
| 협업 | 2/4 참여자, 같은 origin 동시 삽입, 오프라인 후 합류, 중복 전송, 재연결, 양방향 selection |
| 정확성 | 기존 전체 단위·fuzz 시험과 참조 구현 대조. 부분 중복 구간, 서로 다른 삭제 집합, 부분 서식 작성 ID 포함 |
| 시간 | 로컬 편집, 서버 검사·적용, 원격 적용, 모델 변환, 실제 편집기 입력→상대 표시의 p50/p95/최대 |
| 공간 | 힙, 문자 객체 수, 저장 묶음 수, ID 인덱스 항목 수, history 크기, 스냅숏 크기, 재열기 시간 |
| 반복 | 현재와 새 구현을 같은 소스·브라우저·10만 자 조건에서 교차 실행. 방향마다 준비 5회 후 측정 30회. 외부 CPU 부하 기록 |

625문단 초기 데이터에서 문자열 항목 수를 10만 개보다 크게 줄이는 것이 구조 목표다. 모델·서식·편집 경계에 따라 필요한 항목 수는 달라진다. 최악에는 다시 문자 단위에 가까워질 수 있다. 따라서 압축률만으로 성공을 판정하지 않는다. 정확성 통과와 메모리 감소를 확인하고, 지연 회귀가 있는지도 함께 보고한다.

저장 묶음은 문자 항목과 인덱스 비용을 줄일 후보이다. Slate/Lexical 어댑터의 전체 네이티브 문서 재생성은 별도 작업이다. 저장 변경만으로 그 비용이 사라진다고 가정하지 않는다.
