# Continuous-String CRDT Storage Review

- work_id: other-editors-100k-20261022
- Status: live string segments remain a design review. Runtime ID metadata now uses bounded actor ranges; character Items remain separate. See the [metadata report](../../benchmarks/results/metadata-memory-2026-10-24/report.md) for its separate measurement scope.
- Baseline: the working tree on 2026-10-22. Source hashes are recorded in the comparison test's `source-manifest.json`.
- Related results: [Other editor comparison](../../benchmarks/results/monorepo-2026-10-22/other-editors-100k/report.md).

Live string merging remains excluded under the current project decision. The runtime index change does not resume that separate storage design.

## Proposed Decision

**Retain logical IDs and store consecutive string segments in memory.** Split only at boundaries required for edits inside a segment. Never use a segment's physical address for cursors or remote operations.

Input typed one character at a time must also be eligible for merging. Merging only multi-character input is insufficient. Typing, IME commits, and paste have different input units. Storage segments, transport batches, and undo groups are also distinct.

## Facts Confirmed in Current Code

| Layer | Current Behavior | Reference |
| --- | --- | --- |
| Model | Characters with the same marks use a `Run.text` string. | `unitsToRuns`, `canonical` in `crdt/model.ts` |
| Edit generation | Consecutive characters with the same marks become one `text` operation. | `emitUnits` in `crdt/edit.ts` |
| Transport | `Op.text` contains multiple characters. IDs are assigned consecutively from the starting ID. | `Op` in `crdt/doc.ts` |
| Memory storage | `apply(text)` iterates `text.length` times and creates one `Item` per UTF-16 code unit. | `apply` in `crdt/doc.ts` |
| ID lookup | Logical IDs are indexed by actor and ranges of at most 256 IDs. Fragmented sequences use numeric keys. Character Items remain separate. | `crdt/key-index.ts`, `integrate`, `fromSnapshot` |
| Blocks and positions | `TextBlock.chars`, `BlockCache.of`, and `posCache` also use character-level entries. | `blocks`, `replaceBlock`, and position functions in `crdt/doc.ts` |
| Compaction after deletion | Stable consecutive tombstones merge into a `span`. Internal IDs retain lookup semantics; identical range references collapse after GC. | `compact` in `crdt/doc.ts`, `crdt/key-index.ts` |
| Snapshot | Consecutive IDs and origins are omitted, but live characters are still recorded individually. | `itemToJSON` in `crdt/doc.ts` |
| Undo | Input groups can already merge by time and cursor. Target ID lists are stored separately. | `record`, `ExistenceStep` in `crdt/history.ts` |

String transport is therefore already supported. The main review concerns **memory storage and indexes for live strings**. Snapshot size and bulk-deletion transport size need separate stages.

The current 100,000-character test inserts 160 characters per paragraph as one model string, for 625 paragraphs. Storage splits each string into character items. Initial input is not generated by a separate edit call for every character. Additional input during measurement is one character at a time.

## Proposed Storage Unit

This is a conceptual type, not an implementation API.

```ts
type TextSegment = {
  line: LineId;
  actor: string;
  firstLamport: number;
  lengthUTF16: number;
  text: string;                 // Live content. Stable tombstones can be empty.
  firstOrigin: Ticket;
  marks: MarkState;
  deletions: DeletionState;
  compact: boolean;
};
```

The logical ID at offset `i` is `{actor, lamport: firstLamport + i}`. The first character's origin is `firstOrigin`. Each later character's origin is the preceding logical ID from the same actor. Splitting or merging physical segments does not change these values.

Nodes and line heads remain separate items. The body, container interiors, and each table slot retain separate lines. Strings must not merge across different lines or node markers.

### Splitting and Merging

For example, `abcd` with IDs `A:10..13` can be stored as one segment. Inserting `X` after `b` gives storage order `ab | X | cd`. Existing IDs stay unchanged. The origin of `c` remains the original ID of `b`; it does not change to physically preceding `X`.

Split segments at these boundaries:

- Insertion using an internal ID as reference.
- Start and end of deletion, deletion cancellation, or mark changes.
- Node markers, lines, and inline nodes.
- Maximum segment length defined by storage policy.

Merge two adjacent segments only if all conditions hold:

- Same line and actor, with consecutive ID ranges.
- The later segment's first origin is the earlier segment's last logical ID.
- No other item lies between them in RGA order.
- Deletion sets, cancellation sets, GC state, and mark **semantics** match.
- The merged length does not exceed the maximum.

Equal mark values alone are insufficient. LWW write IDs must also be preserved. Initial mark write IDs can differ per character. Compute them with a range-start ID + offset rule, or store separate mark ranges. Two characters that look equally formatted can have different undo eligibility.

Observing remote clocks between typing calls can leave gaps in ID numbers. Do not force a merge in that case. If better compression is needed later, separately consider a higher-level string piece containing multiple ID ranges.

## Required Index and API Changes

Putting a long string in `Item.ch` is insufficient. These paths must also change.

| Current Path | Proposal |
| --- | --- |
| `byKey: Map<string, Item>` | ID-range index per actor. Lookup returns `{segment, offset}`. |
| Character array in `Line.items` | Ordered index of nodes and string segments, aggregating visible and total lengths. |
| `TextBlock.chars` and `BlockCache.of` | String/inline ranges in each block. Remove persistent per-character arrays and reverse Maps. |
| `posCache` | Convert position ↔ logical ID using cumulative range lengths. |
| `rawBlock` / `toJSON` | Generate `Run`s directly from mark ranges without expanding to character objects. |
| `charsBetween` | Return logical ID ranges or a range iterator. |
| `History` | Store internal targets as ID ranges; initially export existing wire ID arrays. |
| Demo per-character DOM access | Render strings, mark ranges, and selection boundaries. Use separate functions for ID and offset lookup. |

Balanced trees and actor-specific range indexes are candidates. The lookup target is `O(log S)`, where `S` is the number of stored segments. Actual costs also depend on splitting, string copying, and mark boundaries. No performance guarantee exists yet.

Keeping existing `Item[]` arrays alongside new indexes would duplicate memory. Compatibility character views must be temporary and created only at requested positions. Avoid caching full character arrays. Tests and UI using `items`, `lines`, `get`, and `TextBlock.chars` are part of the migration scope.

The package currently exports `Item`, `Line`, and `TextBlock`. This is therefore more than an internal data-structure replacement. Define consumer API compatibility and migration timing explicitly. Distinguish compatibility of `Doc.edit`, models, and wire formats from compatibility of data-structure APIs.

Measure maximum segment lengths of 256/1024/4096 UTF-16 units as candidates. No default is selected yet. Shorter segments increase management entries; longer segments can increase partial-edit and copying costs. Do not assume JS engines share strings. Check whether small string slices retain large originals in memory.

## Conditions for Preserving Existing Behavior

| Behavior | Required Conditions |
| --- | --- |
| Concurrent insertion | Use internal origins and ID comparison. Never skip a whole segment by comparing only its first ID. Split at internal insertion positions and conflict boundaries. |
| Partial deletion | Delete only target ID ranges. Exclude characters concurrently inserted by another actor. |
| Deletion cancellation | Cancel only the specified deletion ID. Retain hidden state if other deletions remain. |
| Marks and undo | Preserve LWW write IDs and previous values per range, as well as values. |
| Cursors and selection | Keep logical token keys in `Presence.anchor/focus`. Preserve existing rules for forward, backward, collapsed selections, and boundaries. |
| Enter and paragraph merge | Preserve node markers and boundary rules. String splitting is different from paragraph splitting. |
| GC | Keep server frontiers and undo pins. Retain ordering semantics of internal IDs and origins. |
| Retransmission | Receiving the same text operation again gives the same result. Handle partially existing ID ranges too. |
| Reconnection | Read old logs and snapshots and construct new segments from them. |
| Unicode | Keep UTF-16 as the wire ID increment unit. Distinguish model-path code-point conversion, native UTF-16 positions, and user-cursor grapheme boundaries. |

Include emoji, combining characters, ZWJ strings, and Korean composition. Storage boundaries are not necessarily display-character boundaries. Reassigning current IDs as code-point or grapheme indexes is outside this storage design.

## Compatibility and Order

1. **Change storage only.** Retain `Op.text`, individual logical IDs, and existing JSONL logs. Server and clients use the same range-lookup rules. Initially export snapshots in the existing format. This stage promises no snapshot-size reduction.
2. **Migrate important consumers.** Blocks, positions, model conversion, history, PM, and the demo must consume ranges directly. Do not retain full character-object arrays.
3. **Compare behavior.** Freeze the existing character-storage implementation as a reference. Apply identical operations in multiple causally valid delivery orders. Compare models, logical ID order, cursors, undo, and GC. Different physical segment layouts are allowed.
4. **Change persisted formats separately.** Review range snapshots and del/set ID-range transport. The current protocol has no feature negotiation. Design version/feature negotiation and old-format readers first. Do not repurpose the existing `span` field for new range fields.

Changing transport at the same time makes it difficult to distinguish storage improvements from transport improvements. Use identical logical operations for the first comparison. Treat delayed transmission for input batching as a separate experiment.

## Acceptance Conditions for the Next Implementation

Current measurements are pre-change baselines. String-segment tests in the table below have not run yet.

| Category | Conditions and Checks |
| --- | --- |
| Input batches | Separate 1-, 10-, 100-, and 1000-character insertions. Record comparisons with equal total characters and equal call counts separately. |
| Actual typing | Generate consecutive per-character key events. Candidate intervals: 30/100ms. Record local/remote display, queue accumulation, and final-character arrival. |
| IME / paste | Separate IME commit strings from other multi-character insertion scenarios. Distinguish CDP synthetic composition from actual OS IME. |
| Document shapes | Besides 100,000 characters in 625 paragraphs, test a single 100,000-character paragraph, many small runs, and frequent mark changes. |
| Edit distribution | Start/middle/end, sequential/random insertion, deletion and formatting inside segments, repeated splitting/merging. |
| Collaboration | 2/4 participants, concurrent insertion at the same origin, offline rejoin, duplicate transmission, reconnection, bidirectional selection. |
| Correctness | Existing full unit/fuzz tests and reference comparison. Include partially duplicate ranges, different deletion sets, and partial mark write IDs. |
| Time | p50/p95/maximum for local edits, server validation/application, remote application, model conversion, and actual editor input→remote display. |
| Space | Heap, character-object count, segment count, ID-index entry count, history size, snapshot size, reopen time. |
| Repetition | Alternate current and new implementations with the same source, browser, and 100,000-character conditions. Per direction, 5 warmups then 30 measurements. Record external CPU load. |

The structural goal is to reduce string-item count far below 100,000 for the initial 625-paragraph data. Required item counts depend on model, mark, and editing boundaries. In the worst case, storage can approach character granularity again. Compression ratio alone is therefore insufficient. Confirm correctness and memory reduction and report latency regressions as well.

Storage segments are a candidate for reducing character-item and index costs. Full native-document reconstruction in Slate/Lexical adapters is separate work. A storage change alone cannot be assumed to remove that cost.
